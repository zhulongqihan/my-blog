我做过一次看起来很像“写个接口把现有能力包起来”的任务：把 MapTracker 的能力封装成 REST API，再提供多帧导出。真正开始做以后才发现，接口层并不是给函数套一件 HTTP 外套，尤其是当下游本身有状态、有文件、有耗时操作时。

## 一个能调通的接口还不够

最初的版本很简单：接收参数，调用 MapTracker，返回结果。Postman 里能看到响应，第一眼当然很有成就感。但我很快发现，客户端真正关心的并不只是“有没有返回”，而是返回里的任务状态、文件位置、错误原因和多帧数据是否能被下一步继续使用。

于是我把接口先按使用流程拆开：参数校验、任务创建、核心处理、结果导出、异常返回。每一层都尽量只做自己该做的事，避免把所有逻辑堆在一个路由函数里。这样排查时，才知道到底是参数没有进来，还是下游处理失败。

## 多帧导出会把隐形问题放大

单帧结果很容易验证，多帧结果则会暴露更多细节：帧顺序是否稳定，缺帧如何处理，文件是否被重复覆盖，导出中途失败后客户端拿到的是什么状态。

我后来把导出结果的命名、顺序和返回信息统一起来，并在接口层做了基本的状态约束。接口不假装“所有事情都已经完成”，而是明确告诉调用方当前是在处理、完成还是失败。这样上层业务才能决定是等待、重试，还是把错误展示出来。

这听起来不像什么高级技巧，但接口一旦被真实调用，最先出问题的通常就是这些细节。大家不会因为你的内部函数写得多漂亮而原谅一个下载到一半就消失的文件。

## 延迟低于 200ms 的背后

这条链路最后把端到端延迟控制在 200ms 以内。这个结果不是简单地把 Python 换成异步就得到的，而是逐段看耗时：哪些数据可以提前准备，哪些步骤不必重复做，哪些计算应该放到任务处理而不是请求线程里。

我对“异步”的理解也从这里开始变得具体。异步不是把所有函数都加一个 `async`，而是要先区分请求响应和后台任务：用户需要立刻知道什么，系统可以稍后完成什么，结果完成后如何被可靠地找到。

## 接口设计的最后一公里

如果重新做一次，我还是会先从调用方的真实动作开始设计，而不是先从内部函数的参数开始设计。一个好接口应该让使用者知道下一步怎么走，也应该让维护者在出错时能迅速定位。

把 MapTracker 接进 FastAPI 之后，我留下的不是一套路由，而是一个小小的提醒：接口的价值不在于“能调用”，而在于它是否把能力变成了别人敢于依赖的服务。
