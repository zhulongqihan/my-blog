# 服务启动卡在 20 秒：这次我没有去改 timeout

实习后期帮忙把登录逻辑复用到另一个项目时，项目启动一直卡住。日志里每次等待大约 20 秒，最后报连接超时。这个场景很容易让人顺手去改 `connectTimeout`、增加 retries，或者干脆把某个 IP 写死。

但这次我忍住了。因为“等了 20 秒”本身就是线索：它和配置里的连接超时时间刚好一致，说明程序不是解析失败，而是在尝试连接某个下游 Provider 时一直没有建立连接。

## 先区分解析失败和连接失败

我先确认服务发现地址能正常返回，DNS 和注册中心查询也没有问题。失败发生在拿到 Provider 地址之后，客户端一直连不上具体的服务端口。

这一步很重要。解析失败应该去看域名、注册中心和配置；连接失败则要看网络、VPN、权限和端口是否可达。如果没有先分清楚，后面所有修改都可能只是在“让错误换一种方式出现”。

## 为什么改 timeout 没用

如果目标机器和端口根本不可达，把超时时间从 20 秒改成 3 秒，只会让失败更快；把 retries 调大，只会让失败重复更多次；把 IP 写死，则可能绕过服务发现，却没有解决网络权限本身。

所以我把排查重点放回最底层：当前网络能不能到 Provider，是否需要带特定 VPN，应用运行环境和我本地测试环境是不是在同一条网络路径上。对于这类问题，先用最小的端口连通性验证确认事实，比继续读业务代码有效得多。

## 本地验证要有边界

如果只是想验证新增的登录头逻辑，未必需要把所有依赖 JSF 的服务都在本地启动起来。可以考虑给本地 profile 禁用无关的远端 Consumer，或者对真正要测试的下游提供受控的 Stub；但这些本地便利不能混进预发和生产配置。

这也是我后来逐渐建立的习惯：为了本地开发做的绕行，要有清楚的配置边界，不能因为“我这里能启动”就默认它适合上线。能跑是一种状态，可发布是另一种状态。

## 这次排查留下的判断顺序

以后遇到启动超时，我会按这个顺序看：

1. 是解析不到服务，还是解析到了但连不上？
2. 是代码路径没有执行，还是执行后卡在外部依赖？
3. 当前网络、VPN、权限和端口是否满足条件？
4. 我是在修复根因，还是只是在改变等待时长？

看起来很基础，但工程问题往往就藏在这些基础判断里。不是每一个超时都需要更激进的重试策略，有些超时只是在提醒你：代码已经走到边界之外了。
