# 博客系统技术架构全解析

这篇文章原本只想写一个“我用了哪些技术”的清单，后来发现那样没有太大意义。真正值得复盘的不是技术名词，而是一个小型个人博客为什么最后会长成现在这个样子：前面是 React 页面，中间是 Spring Boot API，后面接着 MySQL、Redis、RabbitMQ 和 Docker Compose，还要考虑文章搜索、点赞、通知、SEO、部署和故障恢复。

它不是一个需要微服务治理的大系统，但它已经足够把很多工程问题集中到一起。对我来说，这个项目更像一张可以反复修改的工程草图：哪里需要一致性，哪里可以接受最终一致；哪些能力应该在线，哪些工作可以异步；一个功能上线之后，谁负责发现它已经坏了。

## 先从访问路径开始拆

用户打开首页时，真正发生的事情并不复杂。浏览器先从 Nginx 拿到前端静态资源，页面再通过 `/api/articles` 之类的接口请求文章列表。文章详情走 `/api/articles/{id}`，搜索、归档和统计则是不同的读路径。

部署到服务器以后，我把前端和反向代理放在同一个 Nginx 容器里，后端、MySQL、Redis、RabbitMQ 分别作为 Compose 服务运行。外部只暴露 80 端口，数据库和消息系统只在本机或 Compose 网络内可见。这样做并不是为了把架构画得漂亮，而是先把边界画清楚：浏览器不应该直接碰数据库，公网也不应该直接碰 Redis。

```text
Browser
   |
   v
Nginx  ---- static assets / uploads
   |
   v
Spring Boot API
   |             |             |
   v             v             v
MySQL          Redis       RabbitMQ
```

## 读路径优先，写路径保持谨慎

博客最频繁的动作是读文章，不是写文章。首页、归档页和文章详情都属于公开读路径，所以我把它们当作第一优先级来优化：查询只取必要字段，摘要列表不加载完整正文，详情接口单独读取内容，热门文章和归档数据使用缓存降低重复查询。

缓存没有被当成“必须存在的第二数据库”，而是 Cache Aside：先读缓存，未命中时读 MySQL，再把结果放回 Redis；更新文章时先写数据库，再清理对应缓存。这样即使 Redis 重启，系统也只是暂时变慢，不会因为缓存丢失而丢文章。这个取舍很适合博客，因为内容的权威副本始终是 MySQL。

点赞、浏览量、限流这些功能就不一样了。它们都可能在短时间内被大量触发，而且一次请求往往包含“判断状态、修改数值、返回结果”几步。如果把这些步骤拆成多个 Redis 命令，中间就可能被其他请求插入。我把这类短小的状态变更放进 Lua 脚本，尽量让一次业务动作在 Redis 内部完成。

## 为什么保留 RabbitMQ

邮件通知、评论提醒这类动作没有必要阻塞用户当前的请求。用户提交评论后，最重要的是评论已经保存，通知可以稍后发送；如果邮件服务暂时不可用，也不应该让评论接口一起失败。因此这部分被放到 RabbitMQ，消费者负责慢任务和重试。

这里的异步不是为了追求“消息队列架构”，而是为了把用户等待时间和外部服务的不稳定性隔开。代价是系统多了一个必须监控的组件，也需要考虑重复消费、失败重试和消息积压。小项目不一定需要 RabbitMQ，但当通知已经影响主请求时，继续把所有事情塞在一个 HTTP 请求里反而更难维护。

## 我没有把它拆成微服务

这是一个刻意的决定。博客的业务边界还没有复杂到需要独立部署用户、文章、评论和通知服务。拆成多个服务会引入注册发现、链路追踪、配置管理和更多部署成本，但不一定会带来对应收益。

现在的拆分方式已经够用：代码按模块组织，运行时按依赖拆容器；需要异步的地方用消息队列隔离，需要快速状态的地方用 Redis 承担，需要持久化的内容留在 MySQL。将来如果评论或 AI 功能真的有独立扩展压力，再考虑把它们拆出去，而不是因为架构图看起来更大就提前分布式。

## 我怎样验证这套结构

验证没有停留在“容器能启动”。我在服务器上保留了一组烟雾检查：首页、`robots.txt`、`sitemap.xml`、文章列表、归档、文章详情应该返回 200，`.env` 和 `/actuator` 等敏感或管理路径应该不能直接暴露。容器层面则要求 MySQL、Redis、RabbitMQ、后端和 Nginx 都通过健康检查。

最近一次 502 故障也说明了这一点：Nginx 本身还在，但 Redis 和 RabbitMQ 退出后，后端无法解析 `redis` 服务名，最终用户看到的是网关错误。问题不是页面突然坏了，而是依赖链没有恢复。把启动顺序、健康检查和烟雾测试放在一起，才比单独看一个容器的 `Up` 状态更可靠。

## 最后留下的判断

这个博客的架构没有什么神秘之处，重要的是每个组件都能说清楚为什么存在。MySQL 负责事实，Redis 负责快速且可丢失的状态，RabbitMQ 负责把慢工作移出主链路，Nginx 负责边界和静态内容，Spring Boot 负责业务规则，React 负责把这些能力变成可用的阅读体验。

我现在更愿意把它称为“可解释的单体应用”。它不追求一开始就拥有最大的扩展性，而是尽量让每一次取舍都能被复盘、被验证，也能在服务器出问题时知道从哪一层开始排查。
