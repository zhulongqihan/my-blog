# 低配云服务器上部署 AI 应用，我做了哪些取舍

低配服务器最诚实的地方，是它不会替你掩盖设计问题。高配机器上一个不合理的常驻服务可能只是多占一点内存，资源紧张时则会直接表现为容器重启、构建超时、数据库响应变慢，甚至让整个网关返回 502。

我把博客和航旅稳定性 AI Agent 都放到云服务器上之后，才真正理解“部署取舍”不是把配置文件写好，而是明确哪些能力必须在线，哪些能力可以慢一点，哪些组件出问题时不能拖垮主站。

## 先拆边界，再谈优化

最初很容易产生一个冲动：既然都是自己的项目，就把所有服务放进同一个 Compose 文件，统一网络、统一日志、统一启动。这样管理确实方便，但也会让资源竞争和故障传播变得更直接。

我的选择是让博客保留一套相对稳定的 Compose 编排，AI Agent 作为独立项目运行。它们可以共享服务器，但不共享一条必须同时成功的启动链路。博客是公开入口，优先保证文章阅读和管理后台；AI 任务则允许排队、超时和降级。

## 哪些服务必须常驻

Nginx、后端、MySQL、Redis 和 RabbitMQ 都有明确的在线职责。Nginx 没有就没有公网入口；后端没有就无法读取内容；MySQL 是文章事实的持久化来源；Redis 支撑缓存、限流和部分短状态；RabbitMQ 负责通知等异步工作。

这不代表它们都同样重要。文章阅读对 Redis 不是绝对依赖，Redis 暂时不可用时可以降级到数据库；而后端对 MySQL 的依赖更直接。依赖关系应该体现在健康检查和启动顺序里，不能只写在文档中。

最近一次 502 就是一个很具体的教训：Redis 和 RabbitMQ 容器退出后，后端无法解析 `redis`，Nginx 便没有可用的上游。后来恢复服务时，我按 Redis/RabbitMQ、后端、Nginx 的顺序启动，并验证每一层健康状态，而不是只重启最外层网关。

## 内存限制不是装饰

Compose 中为服务设置资源上限，目的不是让服务器看起来更专业，而是让异常有边界。Nginx、Redis 和 RabbitMQ 的限制相对小，后端保留更多空间，MySQL 也不能无限制地争抢内存。限制本身不是性能优化，真正有用的是配合日志和健康检查观察：服务是否频繁被杀，JVM 是否发生 Full GC，数据库是否因为内存不足变慢。

我没有在文章里编造一组漂亮的压测数字，因为低配服务器上的结果很依赖当天的 CPU、网络、缓存命中和并发来源。更可靠的做法是记录真实请求路径的响应时间，区分首页、文章详情、AI 请求和后台写操作，然后找出最值得优化的瓶颈。

## AI 功能必须允许失败

AI 请求和普通文章读取的成本不一样。模型调用可能耗时更长，也可能受到上游服务、网络和配额影响，所以不能让首页渲染必须等待 AI。我的页面把 AI 入口做成独立区域，输入为空、接口超时或上游不可用时，博客的阅读路径仍然应该能正常工作。

提示词和 API Key 也不应该散落在前端。浏览器只负责提交用户需求，后端负责校验、限流、调用上游和处理错误。即使这个功能只是个人项目，也应该把密钥放在服务器环境变量里，并在日志中避免打印完整请求和响应。

## 构建也会成为线上风险

低配机器上直接构建后端镜像可能长时间占用 CPU、内存和磁盘 IO。一次构建卡住时，最危险的做法是继续反复执行构建命令，最后把线上容器也拖垮。更稳的流程是先构建、再健康检查新镜像，确认成功后才替换服务；构建超时就保留旧版本，不强制重启健康容器。

这也是我后来坚持保留服务器烟雾检查的原因。部署完成不等于浏览器能访问，至少要验证首页、文章列表、详情、SEO 文件和敏感路径。

低配环境不会阻止一个项目做得完整，但它会要求你对“完整”重新定义：不是组件越多越好，而是边界清楚、失败可控、恢复有顺序。对个人项目来说，这些能力比一张复杂的架构图更有说服力。
