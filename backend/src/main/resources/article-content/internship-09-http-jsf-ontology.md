# 从 HTTP 到 JSF，再到 16 个本体：我重新认识了“接口”

7 月开始接触柔性引擎和面试间本体化时，我原本把任务理解成“把几个 HTTP 接口注册一下”。后来一路跟着套卷、面试间和柔性引擎的设计走下来，才发现真正变化的不是协议名称，而是业务能力被描述和调用的方式。

## 先把一条链路走完整

在套卷场景里，我先从现有后台和数据库关系入手，确认套卷、题目、选项以及它们之间的关联。之后把原有查询能力通过 JSF 暴露出来，再注册为柔性引擎能够识别的对象和接口。

这个过程有很多并不华丽的工作：方法声明和实现要一致，返回结构要补齐，SQL 的状态过滤和去重要对上，前端需要的联动配置要能全量保存和原样返回。真正接入之前，先把这些“接口细节”钉住，后面的本体化才有可靠的地基。

## 本体化不是换个名字

面试间最初被当成一个整体来理解，但一个整体里塞了太多职责：候选人信息、面试考察项、面评、Offer 记录、题目选项和不同页面 Tab 都在互相牵连。后来我们把面试间 Tab 拆成 16 个可以独立注册和调用的业务本体。

这个拆分的价值，不是为了让数字变得好看，而是让每个对象的属性、方法和边界更清楚。AI 或工作流在调用能力时，不需要面对一个什么都能做的大接口，而是可以根据任务找到更贴近业务语义的对象。

## 柔性引擎在这里扮演什么角色

我之前很容易把柔性引擎理解成“新的领域建模框架”。结合会议和代码之后，我更倾向于把它看成数据能力的统一出口：招聘系统内部仍然维护自己的 Biz、Domain 和 Infra，柔性引擎承载对象、Action 和 Function，AIP 再通过这些能力做流程编排。

这样一来，业务系统不必把所有内部实现都暴露给 Agent，Agent 也不需要知道数据库表究竟长什么样。它拿到的是相对稳定、语义更清楚的能力入口。

## 接口变薄之后，系统反而更需要规则

抽象层变多，不代表问题自动消失。相反，方法命名、参数语义、返回结构、状态过滤和幂等规则都要更清楚，否则只是把混乱从一个地方搬到了另一个地方。

这也是我在学习发包和注册流程时最深的感受：一个接口能被调用，不代表它已经适合被复用。只有当它的输入、输出和业务边界都能被别人快速理解，它才真正成为平台能力。

## 这条路为什么值得继续

从 HTTP 到 JSF，再到本体化对象，我看到的是一条从“调用实现”走向“调用能力”的路径。它不会让代码立刻变少，也不会让架构图自动变漂亮，但它会逼着我们把重复接口、隐含规则和模糊边界逐一说清楚。

对我来说，这也是实习后半程最有价值的一次转向：以前我更多是在改一个接口，现在开始思考一个接口应该怎样被系统和 AI 长期理解。
