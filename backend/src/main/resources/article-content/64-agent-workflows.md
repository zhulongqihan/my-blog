# 从提示词到工作流：我对这波 AI Agent 热潮的几个判断

如果把这轮 AI 热潮的变化说得具体一点，我觉得重点不是模型突然拥有了某种神秘的自主性，而是大家开始希望模型完成更长的任务链。用户不再满足于问一句、回一句，而是希望系统能收集信息、调用工具、检查结果、继续下一步，最后交付一个可以使用的产物。

一旦任务变长，问题就从“如何把提示词写得更好”转向“如何设计一个可恢复的工作流”。这是我理解 Agent 时最重要的转折。

## 提示词仍然重要，但它不再是全部

短对话中，提示词决定模型理解什么、采用什么语气和输出什么格式。可是当任务跨越多个步骤后，系统还要记录当前状态、保存中间结果、控制工具权限、处理超时和决定是否重试。这个时候，提示词只是某一个节点的规则，不能代替整个流程。

例如一份航旅稳定性报告，至少要经过输入校验、日志分析、异常归因、证据整理和报告生成。任何一步失败，都需要知道从哪一步继续；如果重复调用某个外部工具，还要防止重复写入或重复发送通知。它已经更像一个有状态的应用，而不是一段更长的文本。

## 先画状态，再设计 Agent

我现在会先问四个问题：任务目前处于什么状态，下一步允许做什么，结果保存在哪里，失败后能否安全重试。把这四个问题写清楚之后，再决定哪些步骤适合交给模型，哪些步骤必须由确定性代码完成。

确定性代码适合做权限校验、参数校验、格式解析、重复请求去重和结果持久化；模型适合做开放式理解、分类、归纳和解释。把前者交给模型会让系统变得不可预测，把后者全部写死又会失去 AI 的价值。

## 工具调用是信任边界

当 Agent 可以访问工具时，模型的错误就不再只是回答错了一句话。它可能选择错误的工具、传入不完整的参数，甚至把用户输入里的恶意内容当成系统指令。因此工具定义需要足够窄，输入需要服务端再次校验，返回结果要和用户输入区分开。

我更倾向于让 Agent 提出“建议动作”，由后端判断动作是否允许执行。只读查询可以自动完成，写入、删除和发送外部通知则需要更严格的权限或人工确认。即使是个人项目，也不能因为数据量小就跳过这层边界。

## 重试不是万能药

工作流里最容易被忽略的是重试。网络超时通常可以重试，但数据库写入、订单创建和发送邮件不一定能重复执行。要区分可重试错误和不可重试错误，还要设计幂等键或状态检查。

我会把一次任务拆成“准备、执行、确认、产出”几个阶段。准备阶段可以重复，执行阶段需要明确动作是否已经成功，确认阶段要根据真实结果判断，而不是根据模型猜测。只有这样，重试才是在恢复流程，而不是把同一个动作重复发出去。

## 结果需要可解释，但不等于暴露全部思维过程

用户需要知道一份结论依据了哪些输入、调用了哪些工具、哪些地方存在不确定性。对工程系统来说，这种可解释性应该体现为结构化证据、工具调用记录和明确的待确认项，而不是要求模型输出一段很长的“内心独白”。

在我的项目里，报告会区分观察到的现象、推断出的可能原因和建议验证动作。这样即使结论后来被证明不对，也能追溯是输入错了、规则不完整，还是模型判断偏了。

## 我认为 Agent 最适合的场景

不是所有功能都需要 Agent。规则清晰、输入结构固定、结果必须完全一致的场景，普通代码通常更可靠。Agent 更适合处理信息来源多、任务需要分步判断、结果需要解释，而且允许人在关键位置接管的问题。

所以我不会为了展示 Agent 而给博客的每个按钮都接上模型。文章搜索不需要 Agent，健康检查不需要 Agent，真正适合的可能是阅读后的写作辅助、复杂内容整理和航旅稳定性分析。

从提示词走到工作流，核心变化不是增加几个角色，而是开始认真面对状态、权限、证据和失败。Agent 如果不能被观察、被限制、被恢复，就很难成为一个值得长期维护的工程系统。
