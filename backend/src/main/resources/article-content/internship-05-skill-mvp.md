刚接触数字员工自动约面时，我列过一长串能力：拉候选人、查面试官日历、找共同空闲、订会议室、发通知、冲突检测、自动改约……列表写得很完整，离真正能跑还很远。

后来我发现，skill 最容易掉进的坑，就是把“以后可能需要的能力”误当成“第一版必须完成的功能”。看起来像规划充分，实际上没有一个清晰的验收终点。

## 先从一轮约面开始

我把第一期收成五步：启动一轮约面，建立或读取跟踪表，拉取候选人，查询面试官和候选人的空闲时间，创建会议并把状态写回表。

邮件通知、京me 通知、冲突改约、看板和日志都先放到后面。不是这些不重要，而是第一期需要先证明：数字员工能不能把一条最小业务链路稳定地跑完。

这个拆分有一个很现实的好处：每一步都能单独观察。是名单没有拉到，还是日历没查到？是会议创建成功但状态没写回，还是调用根本没有走到？当链路只有五步时，问题还在人的理解范围内。

## 多维表不是临时草稿

没有一个正式业务系统跟着整条约面流程时，跟踪表就成了这一轮任务的状态载体。每个候选人用 ERP 作为行唯一键，表里记录预约状态、会议链接和下一步动作，配置文件里保存跟踪表标识。

这个设计看起来朴素，却能解决两个很容易被忽略的问题：上下文变长后，系统不会忘记这一轮到底操作哪张表；某一步失败后，也不会靠大模型“凭感觉”补出一个名单。

我还特别注意到，批量拉取候选人、建表、插入多行这种事情不适合让大模型逐行对话。能脚本化的批量动作就交给 Python 或 CLI，模型更适合处理“这个候选人为什么冲突”“下一步要不要改约”这种需要判断的部分。

## 本地跑通和平台可用是两回事

本地用例跑通后，还要打包上传平台，在真实平台上验证意图识别、权限、接口地址和上下文隔离。期间遇到过已有 skill 和新 skill 串场、接口路径返回 404、HTTP+SSO 方案不能直接复用等问题。

这些问题让我对“能跑”有了更严格的定义：能在自己的会话里跑通，只能说明逻辑有希望；能在干净会话、真实权限和目标平台上稳定复现，才接近可交付。

## 这次 MVP 的意义

MVP 不是把功能砍得越少越好，而是把承诺缩到一个能够被验证的闭环。对我来说，这条约面链路的价值不只是学会怎么写 skill，更重要的是学会先把场景讲清楚，再决定工具和接口应该出现在哪里。

很多复杂系统，都是从一张不太漂亮但确实能更新的跟踪表开始的。先让状态流动起来，再谈自动化的华丽程度。
