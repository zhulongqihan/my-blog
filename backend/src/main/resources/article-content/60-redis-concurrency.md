# Redis 在高并发场景下的实战方案

很多文章介绍 Redis 时，会从缓存、排行榜、分布式锁一路讲到消息队列，最后看起来好像 Redis 可以解决所有并发问题。我的实际体验恰好相反：Redis 最有价值的地方，不是替系统做所有事情，而是把那些需要快速判断、短时间聚合、可以接受最终落库的状态从 MySQL 主链路里拿出来。

博客里的点赞、浏览量、访问限流和热门文章都属于这类问题。它们看起来小，却很容易暴露并发边界：一次请求到底算一次还是多次？同一个访客重复点击怎么办？缓存失效时是否会把数据库打穿？

## 点赞不是简单的加一

一个点赞动作至少包含三件事：判断当前访客是否已经点赞，写入或删除访客状态，更新文章的统计值。如果这三步由多个普通 Redis 命令组成，两个并发请求可能同时判断为“尚未点赞”，然后都执行增加。

我在项目中把这类短事务放进 Lua 脚本，让判断、变更和返回结果在 Redis 内部完成。脚本的输入使用明确的 `KEYS` 和 `ARGV`，不在脚本里动态拼接未知 key。这样一方面能保持原子性，另一方面也方便未来迁移到集群时检查 key 的归属。

```lua
local exists = redis.call('SISMEMBER', KEYS[1], ARGV[1])
if exists == 1 then
  redis.call('SREM', KEYS[1], ARGV[1])
  redis.call('DECR', KEYS[2])
  return 0
end

redis.call('SADD', KEYS[1], ARGV[1])
redis.call('INCR', KEYS[2])
return 1
```

这段逻辑的重点不是 Lua 语法，而是把一个业务动作放在同一个原子执行单元里。Redis 官方文档也明确说明，脚本执行期间具有原子语义，但脚本会阻塞其他 Redis 活动，所以脚本必须短，不能把网络请求或复杂计算塞进去。

## 浏览量应该和文章事实分开

文章正文、标题和发布时间是内容事实，应该落在 MySQL。浏览量则更接近统计状态，没有必要每次请求都同步写数据库。我会先在 Redis 中做短时间聚合，再由异步任务或定时逻辑批量落库。这样可以降低数据库写放大，也避免一个热门文章把数据库写入线程占满。

这也带来一个必须接受的事实：统计数据不是绝对精确的账本。服务器重启、Redis 过期或批量任务失败，都可能让少量浏览量延迟或丢失。对于博客来说这是合理的，因为阅读内容不能丢，浏览统计可以容忍小范围误差。把两类数据混在一起，才是更危险的设计。

## 限流要先定义“谁被限制”

限流不是统一设置一个数字就结束。登录接口应该按 IP 和账号组合考虑，文章点赞更适合按访客标识和文章维度，AI 请求则可能还要按用户或 API Key 限制。key 的维度不清楚，限流器就可能误伤所有用户，或者只挡住一个很容易变化的地址。

我的做法是先在业务层确定限流对象，再用 Redis 记录窗口内的计数。固定窗口实现简单，但窗口边界可能产生突刺；令牌桶和滑动窗口更平滑，却需要维护更多状态。博客的公开读接口不需要很重的算法，真正需要保护的是登录、评论和 AI 生成等有成本的路径。

## 缓存最容易错在失效

读缓存只是开始，更新和删除才是难点。我的文章详情缓存使用“先更新数据库，再清理缓存”的策略。删除缓存比直接改缓存更保守，因为更新逻辑只需要保证下一次读取能拿到数据库的新值，不需要在多个缓存副本之间复制完整业务规则。

如果更新操作和缓存删除之间发生故障，仍然可能出现短暂旧读，所以缓存并不是一致性的最终保证。对文章正文，我宁愿接受短时间的旧缓存，也不会把 Redis 当作唯一数据源。

## 失败场景必须提前写出来

Redis 挂掉时，公开文章应该还能从数据库读取，统计和点赞可以暂时降级；MySQL 挂掉时，不能靠 Redis 假装文章已经保存；脚本执行异常时，要记录具体 key 维度和业务动作，不能只返回一个“操作失败”。这些规则比“用了 Redis”更重要。

最近线上依赖容器退出导致 502，也让我重新确认了一点：缓存组件不是孤立的性能插件，而是应用启动链路的一部分。Compose 的健康检查和依赖顺序要真正覆盖 Redis，后端才能在依赖准备好之后启动。

Redis 适合处理快速、短暂、可重算的状态。理解这个边界以后，缓存、限流、点赞和统计才不会变成一堆互相冲突的技巧。
