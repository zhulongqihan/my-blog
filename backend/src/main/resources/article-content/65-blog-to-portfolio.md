# 从博客到作品集：我怎样把内容线做成可讲述的项目线

我以前做作品集时，习惯把项目链接、技术栈和截图放在一起，然后再补一段“项目介绍”。页面看起来完整，却很难回答一个更重要的问题：这些项目为什么是你做的，它们之间有没有共同的判断。

后来我开始把博客和作品集放到同一条内容线上。文章记录思考过程，项目提供可运行的证据，工程文档解释边界，部署页面证明它们不是停留在本地的半成品。这样整理之后，作品集不再只是结果展示，而更像一条可以被别人顺着阅读的项目叙事。

## 先讲问题，再讲技术

“使用 React、Spring Boot、Redis 和 Docker”只能说明项目用了什么，不能说明项目解决了什么。面试官更可能关心的是：为什么需要 Redis，哪些数据可以缓存，为什么没有拆微服务，服务器资源有限时做了什么取舍。

所以我在文章里尽量先写问题，再写方案。例如博客需要高频读取文章，但文章正文是持久化事实，于是缓存只承担加速而不承担最终存储；通知不应该阻塞评论请求，于是把慢任务放进消息队列；AI 功能可能失败，所以它不能成为首页阅读路径的硬依赖。

这些判断比技术名词更能体现工程能力，因为它们可以被追问，也可以被代码和线上行为验证。

## 文章是项目的决策记录

一篇好的项目文章不应该只是 README 的扩写。它应该保留做决定时的上下文：原来的方案为什么不够，候选方案之间有什么代价，最终选择带来了什么新的问题。

我会尽量把失败也写进去。比如最初可能把所有服务都放在一条启动命令里，后来才发现依赖容器退出时会造成 Nginx 502；又比如一开始把 AI 当成一个炫目的入口，后来把它收束成明确的内容策划和稳定性分析场景。这样的过程比“系统采用最佳实践”更接近真实开发。

## 运行中的证据很重要

作品集里的系统如果只能展示静态截图，别人很难判断它是否真的工作。因此我会保留公开页面、文章详情、健康检查和部署说明，同时准备一组不会破坏数据的服务器烟雾测试：首页、文章列表、归档、SEO 文件和敏感路径都应该有明确预期。

当然，线上运行也不代表系统完美。真实的 502、构建超时、缓存失效和依赖重启，反而提供了更有价值的复盘材料。作品集不需要隐藏所有问题，但要说明如何定位、如何恢复，以及后来怎样降低再次发生的概率。

## 我开始区分三种文档

项目简介回答“这是什么、为谁服务”；架构文档回答“系统怎么运行、为什么这样拆”；文章回答“我在某个具体问题上怎么判断”。三种文档的读者和长度不同，混在一页里会让信息密度失控。

作品集首页应该让人快速找到入口，而不是把所有技术细节一次性塞出来。对真正感兴趣的读者，再提供架构、部署和文章链接。让内容分层，本身也是一种工程设计。

## 这条内容线仍然属于个人表达

作品集不是把自己包装成没有缺点的工程团队，也不是把所有项目都写成商业成功案例。个人项目的价值可以是它展示了一个人怎样学习、怎样拆问题、怎样在资源有限时做决定。

我希望别人读完博客和作品集之后，看到的不只是“会哪些框架”，还包括一条比较连续的成长线：从写文章开始，逐渐把文章里的判断做成系统，再用部署、监控和复盘把系统交付出去。

如果一个项目能让人顺着问题、决策、实现、验证和反思走完一圈，它就不再只是简历上的一行字，而是一段真正可以被讨论的工程经历。
