# 我为什么做了一个航旅稳定性 AI Agent 项目

如果简历里只写“接入过大模型”或者“做过 AI 聊天功能”，现在已经很难说明太多问题。调用接口本身并不复杂，真正困难的是把一个不确定的模型放进一个边界明确、可以演示、也能够解释失败原因的系统里。

我做航旅稳定性 AI Agent，出发点不是再做一个泛用聊天页面，而是给自己找一个足够具体的工程问题。航旅预订链路天然包含多个步骤：搜索、报价、库存确认、下单、支付、出票和通知。任何一个节点变慢或失败，用户看到的可能只是“订单没有成功”，但系统需要知道到底是哪一层出了问题。

## 我先定义的是稳定性问题

项目一开始，我没有直接写提示词，而是先列出需要回答的问题：某个请求失败发生在哪个节点？是超时、参数错误、供应商返回异常，还是内部服务没有及时响应？同样的失败是否在一段时间内重复出现？这次异常有没有影响到其他航线或其他供应商？

这些问题决定了输入不能只有一段自然语言。系统需要接收结构化的链路信息、日志片段、时间窗口和业务上下文，再让模型负责解释、归纳和提出排查方向。模型不是监控系统本身，也不能凭空替代真实指标。

## 我把 Agent 拆成几类职责

第一个角色负责理解用户问题和补齐上下文；第二个角色负责检查链路信息，找出异常节点；第三个角色负责把巡检结果整理成 Markdown 报告；最后由一个汇总角色给出优先级和下一步建议。这样做不是为了让系统看起来更像“多 Agent”，而是因为每个阶段的输入输出更容易单独检查。

如果所有任务都交给一个大提示词，结果出了问题时很难判断是上下文缺失、规则没有命中，还是模型在自由发挥。拆开之后，可以给每个阶段设定较窄的职责：诊断角色不能修改原始日志，报告角色不能凭空增加指标，汇总角色必须区分事实和推断。

## 报告比聊天记录更重要

聊天式回答适合快速探索，但排查问题最终需要一份可以保存、转发和复盘的产物。因此项目输出 Markdown 报告，固定包含问题概览、证据、可能原因、影响范围、建议动作和待确认项。

这种结构会迫使系统回答“依据是什么”。如果输入里没有足够证据，报告应该明确写出信息缺口，而不是用流畅的句子把缺口填平。对稳定性分析来说，“目前无法确认，需要补充某时间段的供应商响应日志”比一个听起来很确定但没有依据的结论更有价值。

## 我没有让模型直接拥有所有权限

Agent 可以建议检查动作，但真正读取数据、调用工具和执行操作仍然由后端控制。工具调用需要校验参数，敏感数据要脱敏，外部结果要标记来源，危险动作则需要人工确认。模型输出只是一个候选结果，不应该直接成为数据库更新或线上操作命令。

这部分工程工作没有演示页面那么显眼，却决定了项目是不是一个可讨论的系统。没有边界的 Agent 只是一个更复杂的聊天框，有边界的 Agent 才能进一步谈状态、审计和故障处理。

## 这个项目最难的不是模型

最难的是把业务问题说清楚。什么叫一次完整的航旅链路，什么算可接受的延迟，哪些错误可以自动重试，哪些错误必须升级人工，报告的读者是开发者、测试还是运营，这些问题如果没有答案，模型能力再强也只能生成一份泛泛的分析。

我也因此把项目和博客联系起来：博客文章负责记录判断，Agent 项目负责把判断做成可运行的流程，部署和监控则负责证明它不是只存在于代码仓库里。三者合在一起，才构成一个比较完整的作品。

## 现在的边界和下一步

目前这个项目更偏向稳定性分析和报告生成，不会假装自己已经覆盖真实航司、供应商和生产流量。下一步如果继续做，我会优先补充可重复的样例数据、评估报告的一致性，以及失败时的人工接管流程，而不是先增加更多 Agent 角色。

我做它的原因很简单：想证明自己不只是会把模型接进页面，而是能够从具体问题出发，设计输入、状态、工具、输出和失败边界。对于一个求职项目来说，这条链路比“用了多少 AI 名词”更值得被看见。
